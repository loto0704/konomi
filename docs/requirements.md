# konomi 要件定義書

最終更新：2026-11-20

konomi（好み）は、Slackのメンバーに「好きなもの・こと」のお題を配信し、モーダルで回答してもらい、集計結果をWebページで共有するSlackアプリ。Apache-2.0のOSSとして公開し、使う組織がそれぞれ自分の環境にセルフホストする。1つの環境で1つのワークスペースを扱う（シングルテナント）。

---

## 1. 概要

- **目的**：メンバー同士の好きなものを知るきっかけを作り、雑談とコミュニケーションを増やす
- **配信タイプ**：チャンネル型（チャンネルの誰でも回答）とDM型（ランダムに選んだ人に個別に依頼）の2種類
- **集計**：Slackの投稿は書き換えず、投稿に付けたリンクから結果ページで確認する
- **提供形態**：OSS ＋ セルフホストのみ。公式ホスティング版（マルチテナント）は作らない
- **基盤**：導入する組織のCloudflare Workers ＋ D1（無料枠で運用できる規模を想定）
- **リポジトリ名**：konomi
- **ライセンス**：Apache-2.0

### MVPの範囲

選択肢型のお題、2つの配信タイプ、配信スケジュール、手動配信、締切（無期限を含む）、匿名／記名をお題ごとに選べる結果ページ、管理画面、セルフホストの手順。

自由記述（「その他」の記入を含む）やリマインドは次の版で扱う。

---

## 2. 用語とロール

| 用語・ロール | 意味 |
| --- | --- |
| ワークスペース | konomiを導入した1つのSlackワークスペース。1つの環境につき1つ（`SLACK_TEAM_ID` で指定） |
| 導入者 | konomiを自分のCloudflareとSlack Appでデプロイする人。多くの場合、管理者を兼ねる |
| 管理者 | 環境変数 `ADMIN_USER_IDS` で指定した人。管理画面から他の管理者を追加できる |
| 回答者 | お題に回答する人。チャンネル型では対象チャンネルのメンバー全員、DM型では選ばれた人 |
| お題 | 質問文と選択肢（2〜4個）。おすすめの配信タイプ（チャンネル向け／DM向け／どちらでも）と、結果の表示方法（匿名／記名）を持つ |
| 配信スケジュール | 配信タイプ、頻度、時刻、締切、人数などの定期配信の設定。複数作れる |
| 配信（ラウンド） | 1回分のお題の配信。配信タイプ、対象者、締切、状態（受付中／終了）を持つ |
| チャンネル型 | 対象チャンネルにお題と「回答する」ボタンを投稿し、誰でも回答できる配信 |
| DM型 | 対象チャンネルのメンバーからランダムに選んだ人に、DMで個別に依頼する配信 |

## 3. 機能要件

配信タイプは配信ごとに決まり、お題は「おすすめの配信タイプ」だけを持つ。設定値はすべて管理画面から変更できる。

### 3.1 お題管理

- 形式はMVPでは**選択肢型（2〜4択）**のみ。次の版で自由記述と「選択肢＋その他の記入」を足せるよう、お題に回答の形式を持たせておく
- 結果の表示方法（**匿名**／**記名**）をお題ごとに選べる。初期値は匿名。配信時の設定を配信に記録し、あとでお題の設定を変えても過去の配信の表示は変わらない
- 日本語のお題を数十個、初期データとして同梱する
- 管理画面で追加・編集・無効化できる
- おすすめの配信タイプ（チャンネル向け／DM向け／どちらでも）を設定できる
- 配信済みかどうかを記録し、定期配信では未使用のお題を優先する

### 3.2 配信スケジュール

| 項目 | 内容 | 初期値 |
| --- | --- | --- |
| 作成数 | 複数作れる | ― |
| 配信タイプ | チャンネル型／DM型 | チャンネル型 |
| 頻度 | 曜日と時刻（設定したタイムゾーン） | 平日 10:00（仮） |
| 祝日 | スキップするかどうか | スキップする |
| 締切 | 時刻指定、配信からN時間後、または無期限 | 当日18:00（仮） |
| 人数（DM型のみ） | 1回に選ぶ人数。チャンネル型は人数の制限なし | 3人 |
| お題の選び方 | 配信タイプに合う未使用のお題からランダム | ― |
| 有効／停止 | スケジュールごとに一時停止できる | 有効 |

### 3.3 配信タイプ

- **チャンネル型**：対象チャンネルは1つ。お題と「回答する」「結果を見る」を投稿し、チャンネルのメンバーなら誰でも回答できる（除外対象の人を除く）
- **DM型**：対象チャンネルのメンバーから、除外対象を除いてランダムに選び、一人ずつDMで依頼する。回答できるのは選ばれた人だけ

### 3.4 対象者と除外

| 区分 | 条件 | 変更 |
| --- | --- | --- |
| 必ず除外 | Bot、削除されたユーザー、Slack Connectの外部ユーザーなど、送信できないユーザー | 不可 |
| 設定で除外 | 過去N日以内に選ばれた人（DM型） | 可（初期値7日、0で無効） |
| 設定で除外 | ゲスト | 可（初期値は除外） |
| 設定で除外 | 管理者が指定した人 | 可 |
| 本人が選ぶ | 参加しない設定（オプトアウト）にした人 | 本人がいつでも元に戻せる |

### 3.5 回答

- ボタンを押すとモーダルが開き、選択肢から1つ選んで送信する
- 1人1回答。締切までは回答を変更できる
- 送信時にサーバー側で、ワークスペース、締切前か、回答できる人かを確認する。対象外の人には本人だけに見えるメッセージで知らせる
- 記名のお題では、回答が名前付きで結果ページに表示されることをモーダルで示す
- 回答後は「回答ありがとうございます」と結果ページへのリンクを表示する

### 3.6 締切

- 配信ごとに締切を選べる。無期限（常設）も可
- 受付中の配信は、管理画面から手動で終了できる
- 同時に受付中にできる無期限の配信は、初期値**10件**。管理画面から変更できる
- 締切になったら、元の投稿のスレッドに結果の概要とリンクを1件投稿する（元の投稿は書き換えない）

### 3.7 結果ページ

- Sign in with Slackでログインし、同じワークスペースのメンバーだけが見られる
- 票数と割合を表示する。匿名の配信では誰がどれを選んだかは出さない
- 記名の配信では、集計に加えて選択肢ごとに回答者の名前を表示する。名前はDBに保存せず、表示のたびにSlackから取得する
- 過去の配信の一覧と、それぞれの結果を見られる

### 3.8 管理画面

- 管理者だけが使える（`ADMIN_USER_IDS` で指定した人 ＋ 管理画面で追加した人）
- お題、配信スケジュール、対象チャンネル、タイムゾーン、除外条件、管理者、無期限配信の上限、データの保存期間を設定できる
- 配信の一覧と手動終了
- **記名での回答を確認できる**（管理者のみ。回答者には「管理者が確認できる」ことをモーダルで示し、導入者向けのREADMEにも明記する）

### 3.9 手動配信とコマンド

- `/konomi`：管理者がすぐに配信する。モーダルでお題、配信タイプ、締切を選ぶ（配信タイプの初期値はお題のおすすめ）
- `/konomi optout`／`/konomi optin`：本人が参加しない設定を切り替える
- コマンド名は仮（未決事項）

## 4. 画面とメッセージの流れ

```
[チャンネル型] チャンネルに投稿（誰でも回答）──┐
                                              ├─▶ [回答ボタン → モーダル] ─▶ [サーバーで確認・保存]
[DM型] ランダムに選んでDM ─────────────────────┘     選択肢から1つ選ぶ        対象者・締切・1人1回答
                                                                                   │ 締切まで回答を変更できる
                                                                                   ▼
[結果ページ] ◀── [スレッドに結果を投稿] ◀────────────────────────────── [締切または手動終了]
ログイン必須・匿名か記名で集計   元の投稿は書き換えない                          無期限は手動で終了
```

結果ページは、投稿の「結果を見る」リンクからいつでも開ける。

### メッセージの例（チャンネル型）

```
今日のお題：犬派？猫派？（締切 18:00） [回答する] [結果を見る]
  └（スレッド）締切です。猫 58% / 犬 42%　[結果を見る]
```

## 5. データ設計

1つの環境が1つのD1データベースを持ち、1つのワークスペースのデータだけを入れる。Slackのトークンなどの秘密情報はDBに保存しない。日時はUNIX時間（整数）で保存する。

| テーブル | 主な項目 | 制約・インデックス |
| --- | --- | --- |
| settings | id（常に1）, channel_id, timezone, exclude_recent_days, include_guests, max_open_unlimited（初期10）, retention_days | PK: id |
| admins | user_id, added_by, added_at | PK: user_id |
| user_preferences | user_id, opted_out, excluded_by_admin | PK: user_id |
| topics | id, question, recommended_type, answer_format（MVPは選択肢のみ）, result_visibility（匿名／記名）, is_active, last_used_at | IDX: is_active |
| topic_choices | id, topic_id, label, position | IDX: topic_id |
| schedules | id, type, days_of_week, time, skip_holidays, deadline_rule, dm_count, is_active, next_run_at | IDX: (is_active, next_run_at) |
| rounds | id, topic_id, schedule_id, type, result_visibility（配信時のお題の設定を記録）, channel_id, message_ts, deadline_at（無期限はNULL）, status, created_at | IDX: status, (status, deadline_at) |
| round_targets | round_id, user_id, dm_channel_id, message_ts | PK: (round_id, user_id) |
| answers | round_id, user_id, choice_id, answered_at, updated_at | UNIQUE: (round_id, user_id) |
| sessions | id, user_id, expires_at | PK: id, IDX: expires_at |
| login_states | state, nonce, expires_at | PK: state |

- **二重回答の防止**：`answers` のユニーク制約。再回答は `ON CONFLICT` で選択肢を上書きする
- **集計**：結果ページで `answers` を `GROUP BY choice_id` で数える
- **過去N日以内に選ばれた人**：`round_targets` と `rounds.created_at` から判定する
- **定期配信の二重実行防止**：`schedules.next_run_at` を条件付きで更新できた場合だけ配信する
- **複数の書き込み**：D1はSQLのトランザクション（`BEGIN`／`COMMIT`）を使えないため、`batch()` でまとめて実行する
- **管理者**：`ADMIN_USER_IDS` の人は常に管理者として扱い、`admins` には管理画面で追加した人を入れる

## 6. 技術構成

```
                    ┌──────── Cloudflare Workers（1つのWorker）────────┐
[Slack] ──操作────▶ │ Slack受付       署名検証・3秒以内に応答            │
   ▲                │ Cron（5分おき） 配信時刻が来たものを抽出           │ ◀──▶ [D1（SQLite）]
   │                │      │ Queuesで小分け                              │
   └──投稿・DM───── │ Queue受信       1件ずつ投稿・DM送信                │ ───▶ [Secrets] トークン・署名鍵
[ブラウザ] ───────▶ │ Web             結果ページ・管理画面・ログイン     │
 Slackでログイン    └────────────────────────────────────────────────────┘
```

Slackの受付、定期配信、Web画面を1つのWorkerで扱い、時間のかかる送信はQueuesで小分けにする。

| 項目 | 選定 |
| --- | --- |
| 言語 | TypeScript |
| フレームワーク | Hono |
| Slack連携 | `slack-edge`（Workers対応）、または署名検証を自前で実装 |
| DB | Cloudflare D1 ＋ Drizzle（マイグレーションはWranglerで適用） |
| 定期実行 | Cron Triggers（5分おき）＋ Queues |
| 画面 | Hono JSXでサーバー側から画面を返し、Slack用の処理と同じWorkerで配信する（管理画面が複雑になったら、同じWorkerからReactを配信する） |
| ログイン | Sign in with Slack（OpenID Connect）＋ 自前のセッション |

### 設定値

| 名前 | 種類 | 内容 |
| --- | --- | --- |
| `SLACK_BOT_TOKEN` | Secret | Botトークン |
| `SLACK_SIGNING_SECRET` | Secret | Slackからのリクエストの署名検証 |
| `SLACK_CLIENT_ID`／`SLACK_CLIENT_SECRET` | Secret | Sign in with Slack |
| `SESSION_SECRET` | Secret | セッションの署名 |
| `SLACK_TEAM_ID` | 変数 | 受け付けるワークスペース |
| `ADMIN_USER_IDS` | 変数 | 最初の管理者（カンマ区切り） |
| `APP_BASE_URL` | 変数 | 結果ページ・管理画面のURL |

手元の開発では `.dev.vars` に置く（リポジトリには `.dev.vars.example` だけを置く）。

### Slack Appの設定

導入者は `manifest.yml` からSlack Appを作り、Slack Appの設定画面から自分のワークスペースにインストールする。OAuthのインストール画面は作らない。

| 種類 | 内容 | 用途 |
| --- | --- | --- |
| Botスコープ | `chat:write` | チャンネル投稿、DM、スレッドへの結果投稿 |
| Botスコープ | `commands` | `/konomi` コマンド |
| Botスコープ | `channels:read`、`groups:read` | 対象チャンネルのメンバー取得（公開／非公開） |
| Botスコープ | `users:read` | Bot・削除済み・ゲスト・外部ユーザーの判定 |
| ログイン用スコープ | `openid`、`profile` | 結果ページ・管理画面のログイン |
| インタラクティビティ | ボタン、モーダル送信 | 回答 |
| App Home | メッセージタブを有効化 | DM型の依頼 |

スコープは実装時に必要最小限かを再確認する。

### 環境（開発者自身の環境）

| 項目 | 開発用 | 本番用 |
| --- | --- | --- |
| Worker | `konomi-dev` | `konomi` |
| D1 | `konomi-dev-db` | `konomi-db` |
| Slack App | 開発用のSlack App | 本番用のSlack App |
| Secrets | 開発用 | 本番用（別の値） |
| URL | `konomi-dev.<アカウント>.workers.dev` | workers.dev、または独自ドメイン（任意） |

- Wranglerの設定で環境ごとに書き分ける（`env.dev`／`env.production`）
- マイグレーションは開発用で確認してから本番に適用する
- 手元では `wrangler dev` とローカルのD1で確認する

## 7. セキュリティ・プライバシー

秘密情報はSecretsに置く、ワークスペースを照合する、ログインを必須にする、の3点はMVPから入れる。

| 項目 | 対策 |
| --- | --- |
| Slackのトークン | DBに保存せず、WorkersのSecretsに置く |
| ワークスペースの照合 | Slackからのリクエストと、ログインした人の `team_id` が `SLACK_TEAM_ID` と一致するか確認し、違えば拒否する |
| Slackからのリクエスト | 署名とタイムスタンプ（5分以内）を検証し、リプレイ攻撃を防ぐ |
| ログイン（結果ページ・管理画面） | Sign in with Slack（OpenID Connect）。`state` と `nonce` を発行し、`id_token` の発行元・宛先・`nonce` を検証する |
| セッション | `HttpOnly`・`Secure`・`SameSite=Lax` のCookieで管理し、localStorageにトークンを置かない。有効期限30日。更新系のAPIはCSRF対策をする |
| 管理者の権限 | 管理画面のAPIでは、毎回管理者かどうかを確認する。記名の回答を見られるのは管理者だけ |
| 外部スクリプト | ログインが必要なページに広告など外部のスクリプトを載せない。CSPを設定する |
| ログ | トークンや回答内容をログに出さない |
| 依存ライブラリ | Dependabotで自動更新。ライブラリは少なく保つ |
| 導入者の責任 | Cloudflare・Slack App・Secretsの管理と、アップデートの適用は各組織が行う。READMEとSECURITY.mdに注意点を書く |

### データの保存期間

- 回答は記名で記録し、結果ページでは配信ごとの設定（匿名／記名）に従って表示する
- 回答は1年で自動削除（管理画面から変更可）
- 期限切れのセッションや `login_states` は定期的に削除する
- 利用をやめるときに、Worker・D1・Slack Appを削除する手順をREADMEに書く

## 8. 非機能要件と制限

1つのワークスペースで数百人規模、1日数回の配信なら無料枠に収まる見込み。上限を超えるとD1へのクエリが失敗して止まるため、大きな組織にはWorkersの有料プラン（月5ドル）をREADMEで勧める。

| 制限 | 内容（無料プラン） | 対策 |
| --- | --- | --- |
| Workersのリクエスト数 | 1日10万回 | 利用量を監視する |
| WorkersのCPU時間 | 1回あたり10ミリ秒 | ライブラリを小さく保つ。署名検証などは標準のWeb Cryptoを使う |
| 1回の処理での外部リクエストとD1クエリ | 各50件まで | Cronは配信対象の抽出だけ行い、送信はDMの宛先ごとにQueuesで小分けにする |
| Cron Triggers | アカウントあたり5個、UTCで動作 | 5分おきの1個だけ使い、アプリ側でタイムゾーンを変換する |
| Queues | 1日1万回、保存期間24時間 | 配信の小分けにだけ使う |
| D1の読み書き | 読み取り1日500万行、書き込み1日10万行 | 絞り込みに使う列に必ずインデックスを張る |
| D1の容量 | 1DB 500MB（有料プランは10GB） | 古い回答を保存期間で削除する |
| Slackの投稿 | 1チャンネルに1秒1件、ワークスペース全体で1分数百件 | 429が返ったら `Retry-After` の秒数だけ待って再送する |
| Slackへの応答 | 3秒以内。モーダルを開く `trigger_id` も3秒で無効 | ボタンが押されたら先に `views.open` を呼ぶ。重い処理は `waitUntil` やQueuesに回す |
| Slackの再送 | 応答が遅いと同じイベントが再送される | 同じ処理を二重に行わない作りにする |

**バックアップ**：D1のTime Travelで過去の任意の時点に戻せる（無料7日、有料30日）。必要に応じてSQLとして書き出し、R2に保存する手順をREADMEに書く。

## 9. OSS公開・セルフホスト方針

konomiはセルフホスト専用のOSSとして公開する。各組織が自分のCloudflareとSlack Appで動かし、データも各組織の環境に残る。

| 項目 | 方針 |
| --- | --- |
| 提供形態 | セルフホストのみ。公式ホスティング版（マルチテナント）は作らない |
| 導入の流れ | ① リポジトリを取得 ② `manifest.yml` からSlack Appを作り、自分のワークスペースにインストール ③ CloudflareでD1を作成し、Secretsを設定 ④ デプロイ ⑤ Slack AppにWorkerのURLを設定 |
| fork | 不要。設定はWranglerの設定とSecretsで行う。各自の設定は非公開のデプロイ用リポジトリで管理できる |
| 導入を楽にする仕組み | 画面キャプチャ付きのセットアップ手順、D1の作成・マイグレーション・Secretsの設定を対話式で行う初期化スクリプト、GitHub Actionsのデプロイ例 |
| アップデート | GitHub Releasesでバージョンを公開し、変更点とマイグレーションの有無を書く |
| DBの差し替え | 最初はD1に絞る。データアクセスは1か所にまとめ、SQLiteファイルやPostgresへの対応は需要が出てから |
| リポジトリに入れるもの | `manifest.yml`、README（セットアップ手順）、`.dev.vars.example`、Wranglerの設定例、サンプルのお題、`LICENSE`、`CONTRIBUTING.md`、`SECURITY.md` |
| ライセンス | Apache-2.0（特許の利用許諾があり、名前やロゴの使用は許可しない） |
| 収益化 | 行わない。GitHub Sponsorsなどの寄付のみ |
| Slack Marketplace | 掲載しない |
| 監視 | Workersのログ |
| Discord対応 | 対応する場合は同じリポジトリで、共通処理（core）とプラットフォームごとの部分を分ける。中心の処理はSlackに依存させない |
| マルチテナント | 当面作らない。要望が多ければ検討する |

### 進め方

1. 自分のワークスペースで開発し、試す
2. セットアップ手順と初期化スクリプトを整えて、OSSとして公開する
3. 利用者の声をもとに改善する
